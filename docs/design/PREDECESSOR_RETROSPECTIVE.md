## 2. 提交史画像

### 2.1 A：六周 62 个版本的“审计—复盘—修补”循环

A 的开发循环是：审计一个真实项目 → 复盘 → 写一套当版设计件 → 实现若干修复 → 同步版本链 → 找一个新项目做验收审计 → 回到复盘。

| 提交主题（多标签） | 约占提交 | 这些提交在解决什么 |
|---|---:|---|
| 提示词、任务书、清单的条款增补 | 31% | 每轮复盘把新观察写成新的条款或清单条目 |
| 发现能力建设 | 27% | 新的机制族、签名、语言问题矩阵、探针模板 |
| 测试用例与守卫 | 26% | 每版新增一份版本专属测试文件 |
| 审计经验回灌 | 26% | 把审计得到的教训、覆盖账本计数、矩阵条目写回 skill 资产 |
| 版本链同步 | 23% | 版本号、版本守卫测试行、增量段、追踪表、资产计数 |
| 当版设计文档套件 | 21% | 每个小版本一套 4–5 份设计件 |
| 判定与证据等级逻辑修补 | 21% | 证伪资格、实证保真度、声称分类、降级与复活 |
| 路径、安装与双副本漂移 | 16% | 相对路径、开发副本与已安装副本不一致 |
| 簿记与队列状态 | 11% | 覆写、ID 碰撞、去重、旧队列兼容 |
| 输出形态容错 | 9% | 为 worker 输出的字段名与形态变体添加归一器 |
| 规模与预算适配 | 9% | 规模档位、任务文件化、截断协议 |
| 报告渲染 | 8% | 分级映射、默认值兜底造成的误渲染 |
| 覆盖率口径 | 6% | 分母与口径不一致 |
| 去项目化整改 | 4% | 清理进入运行时资产的项目名、路径、专名，并扩充黑名单 |

读法：

- **同步工作挤占了大量提交。** 版本链、当版设计件、路径与双副本三类合计涉及约 55% 的提交。到后期，每发一个版本要同步 20–26 处版本守卫测试行，外加增量段、追踪表和资产计数。
- **修复以加法为主。** 新条款、新归一器、新黑名单词条不断叠加。入口文档曾涨到 2,025 行，一次性迁出 38 个历史增量段后降到 596 行（提交 `e9ec77b`），此后 12 个版本又涨回 705 行。
- **去项目化是反复整改，没有一次解决。** 先后出现过“一次清理 36 条绝对路径”（`0ff669b`）、“一次整改 15 处”、“黑名单漏了三个专名后补词条”（`acfcb92`）。提交数占比不高，但每隔几个版本就复发。
- **审计期会写已安装副本。** 覆盖账本和知识矩阵在审计收尾时回填，写入点是已安装的 skill 目录，于是出现“开发副本滞后、两份副本取并集同步”这类提交。

### 2.2 B：重写后的大部分提交在加固运行时自身

B 是对 A 的重写：单一 schema、事件存储、任务租约、可恢复的 Campaign/Batch。

| 提交主题（单标签） | 约占提交 | 这些提交在解决什么 |
|---|---:|---|
| 状态与计划完整性校验 | 17% | 给计划、清点、交接、边界归属、写一次工件逐项补校验 |
| 文档与完成状态追踪 | 15% | 记录阶段验收状态、剩余门禁、重估结论 |
| 重试、恢复、幂等、修订 | 13% | 部分提交可重试、阶段修订溯源、下游失效与重排 |
| 结构性重构 | 11% | 拆分命令处理器与结案门禁 |
| 仅测试 | 9% | 大规模事件、回滚、任务枚举的专项测试 |
| 成本与输出体积 | 8% | 输出上限、任务输入压缩、扇出控制、工作单元尺寸 |
| 试点暴露的流程契约修复 | 8% | 真实试点中发现的裁决、对账、结案问题 |
| 声明式覆盖 | 5% | review altitude、路径风险分层等自我声明字段 |
| 通用性与偏置清理 | 4% | 删除写死的项目名列表、清除试点带入的指导措辞 |
| 实验来源证明 | 4% | 签名的外部观察、宿主 worker 认证 |

读法：

- **约七成提交服务于运行时自身**（状态校验、恢复、重构、状态文档、声明式覆盖、专项测试）。直接提升发现能力的提交很少。
- **校验越补越多。** 109 个提交集中在一天，其中 31 个在给状态对象补校验（整个历史里这类提交全部发生在这一天），19 个在处理重试与恢复，15 个是结构性重构。状态模型越大，需要校验的不变量越多。
- **运行时规模随之膨胀。** 当前有 80 个 CLI 子命令、2.4 万行运行时代码和 2.1 万行测试；协调者需要加载的入口文档加运行手册共 91KB。
- **输出体积最早暴露问题。** 一个工作单元若有五千多条必须逐项表态的边界审查，最小合法输出约 1.48 MiB，超过当时的上限而无法提交（`9886b37`）；要求模型压缩体积后，覆盖率掉到 34%（`dc90c4d`）。
- **真实试点后转向清理偏置。** 多个提交在把共享指导改回中性措辞，或把项目试点记录与通用流程分开（`c90664f`、`8eb3db4`、`a0d3179`）。

### 2.3 C：提交少，每个都指向一个可复用的设计点

| 提交主题 | 解决的问题 |
|---|---|
| 把 skill 文件移入独立子目录 | 仓库根与载荷混放，通用安装器无法安装 |
| 校验 trace 步骤顺序（`71e1549`） | 证据链可以乱序或缺 sink 而通过校验 |
| 新增内存安全、AI、Web 协议、客户端等领域文件 | 领域知识按文件拆分，按需选用 |
| 全 skill 统一风格 | 散文里的严重度写法与 schema 枚举不一致；同一概念多个名字；动态确认的范围未说明 |
| 端到端重做（`158eb44`） | 三分支裁决契约；确定性覆盖账本；覆盖复核波次；预算预留；显式的未完成状态；沙箱与产物转存规程；输出默认放在目标仓库之外；校验器加固；提示词补上终止条件、探索深度上限和字面返回格式 |
| 区分 guidance 与 full audit 两种模式（`c1c8a8c`） | 加载 skill 就启动完整流程并写文件 |

读法：C 用 Markdown 指令加两个零依赖校验器完成了一套完整流程，指令清晰、契约单一。它的局限在规模：覆盖账本是由父 agent 手写的单个 JSON 文件，校验器上限是 5 MiB、1,000 条发现；每个 hunter 的提示词要原样拷入架构摘要、选中的攻击类正文和一段 hunter 自己并不执行的转存规程。

## 3. 问题类目与设计对策

处置方式三选一：

- **消除前提**：新架构里不再存在产生该问题的机制。
- **针对设计**：机制保留，增加专门的约束或检查。
- **接受**：不处理并说明理由（本表没有这一类）。

| 编号 | 问题与来源 | 根因 | 处置 | 新设计中的对策 | 设计章节 |
|---|---|---|---|---|---|
| P-01 | worker 输出形态漂移，靠容错归一器追赶（A：“双形态、三形态、键名归一”；B：字段名近似即被拒） | 输出契约写在散文里；校验发生在 worker 上下文结束之后 | 消除前提 + 针对设计 | 每类记录一份 schema，提示包内嵌同一份；提交时严格校验，失败在原会话修复；不写归一器 | §13.4、§15.3 |
| P-02 | 簿记与状态覆盖（A：覆写、ID 碰撞、去重） | 多个阶段共同改写同一份可变 JSON 队列 | 消除前提 | 只追加事件，单一归约函数；ID 确定性生成；视图全部派生 | §4.4、§10 |
| P-03 | 覆盖率口径与分母错误（A） | 多处各自计算覆盖率 | 针对设计 | 分母只来自冻结清点，分子只来自已校验记录，由一个函数计算 | §5.5 |
| P-04 | 报告失真（A：默认值兜底把“已复核无问题”渲染成中危；B：报告 2.6MB，发现排在一万四千行之后） | 缺失字段用默认值填充；过程明细与结论混排 | 针对设计 | 报告由记录机械派生，缺字段即校验失败；发现优先的编排与体积预算；黄金文件测试 | §9 |
| P-05 | 路径、安装与双副本漂移（A） | 审计期向已安装副本写入；相对路径；两份副本 | 消除前提 | 载荷只读、单一可安装目录；路径由工具包解析为绝对路径；运行期零写回 | §3.2、§13.1 |
| P-06 | 版本链与当版设计件的同步开销（A） | 版本号散落在测试、文档、资产计数里；每版一套文档 | 消除前提 | 单一版本文件；设计文档就地更新，加追加式决策记录；测试不断言版本号与资产计数 | §17 |
| P-07 | 条款堆积与入口文档膨胀（A、B） | 每次复盘的观察直接写成全局条款，没有容量上限 | 针对设计 | 文本与机制预算由 CI 强制；指导挂到卡片上按适用条件加载；新增内容过准入问题清单 | §6.3、§15.4、§17 |
| P-08 | 审计经验回灌带入项目信息并造成知识偏置（A：回填与反复的去项目化整改；B：试点措辞进入通用指导） | 存在“审计 → skill 资产”的写回通道；黑名单只能事后补词条，而且黑名单本身就记录了被审项目名 | 消除前提 + 针对设计 | 运行期无写回；自审报告分可移植与本地两部分，可移植部分过泄漏检查；知识条目采用正向准入；仓库内不存放任何真实项目名单 | §11、§12 |
| P-09 | 判定与证据等级逻辑反复修补（A） | 裁决、证据强度、声称类型揉在一组相互影响的字段里 | 针对设计 | 三种裁决加独立的证据等级；转移规则表驱动并逐条测试；无证据不升级 | §8.4、§8.5 |
| P-10 | 门禁停留在文字，或恒为真（A：门禁步骤未进入断言；B 的评价报告：三个恒真门禁与自证测试） | 门禁靠 agent 自觉执行；检查的是形状而非内容 | 针对设计 | 门禁全部是工具包命令并以退出码表达；每个门禁至少一个必须失败的反例夹具 | §4.5、§16 |
| P-11 | 测试污染资产，夹具取自真实项目（A） | 测试写共享资产；回归锚点来自被审项目 | 消除前提 | 测试只写临时目录；夹具全部为合成代码 | §16 |
| P-12 | 强制全量枚举导致输出爆炸（B） | 要求模型对每条边界、每个轴、每个类别逐项表态 | 消除前提 | 枚举由程序完成；模型只输出阳性与例外；输出上限写进 schema | §6.4 |
| P-13 | 运行时为自身状态不断加固（B） | 状态模型过大：计划修订、阶段修订、交接对象、追加式修正 | 消除前提 | 状态只保留 run、unit、task、candidate、finding；不支持修订，受影响部分直接重算 | §4.4 |
| P-14 | 重试、恢复、幂等的复杂度（B） | 由 LLM 协调者领取任务并持有租约；校验失败只能整份重做 | 消除前提 | driver 直接持有 worker 进程的生命周期，没有租约；任务 ID 确定性；结构错误在原会话修复 | §5.8、§13.4 |
| P-15 | 只能校验形状的声明式保证（B：review altitude、风险分层、签名观察、宿主认证） | 用 agent 的自我声明代替观测 | 消除前提 | 能从宿主日志观测的（打开了哪些文件、用量）一律观测；不能验证的声明不收集；不做签名与认证 | §5.5、§6.8 |
| P-16 | LLM 协调者负担与简报漂移（B：80 个子命令；自审账本记录了简报沿用上一批的叙述、结果路径写错、限流下后台 worker 静默死亡） | 长循环在模型上下文里运行；协调者手写简报 | 消除前提 | 调度循环是程序；提示包由模板确定性渲染；结果经进程输出返回，worker 不写文件；限流退避与熔断 | §3、§5.8、§13 |
| P-17 | 无效任务扇出（B，数据见本文 §4.1） | 按“阶段 × 对象”建任务，不看是否有事可做 | 消除前提 | 取消独立的类别复审阶段和逐假设的实验评估阶段；任务只在有输入时创建 | §4.3、§6.5 |
| P-18 | 知识库模板化（B 的评价报告：150 条中约七成是通用弱点标签，只有 18 条含语言特有 API） | 条目由迁移脚本生成并按名次截断 | 针对设计 | 语言特异性检查、去样板检查；每张卡配合成正反例与信号 | §7.4 |
| P-19 | 类别名单被当成围栏（B：选定类别之外的假设被拒收） | 把关注重点实现成了白名单 | 针对设计 | 目录只用于引导与排序；目录外候选一律可报告，并计入自审 | §7.5 |
| P-20 | 用量不可测（B，数据见本文 §4.1） | 依赖 worker 与宿主自报 | 针对设计 | driver 从 CLI 输出里机械读取用量 | §6.8 |
| P-21 | 结论不可判定（B，数据见本文 §4.2） | 决定性的一步在切片之外；“待复核”没有结构 | 针对设计 | 验证者不受单元限制；阻断事实用封闭枚举加验证计划；允许带明确前提的静态确认并标注证据等级 | §8.4–§8.6 |
| P-22 | 状态追踪型文档提交（B） | 用文档记录完成状态 | 消除前提 | 状态由测试与 CI 表达；只保留变更日志 | §17 |
| P-23 | 分发目录与安装器不兼容（C） | 载荷与仓库根混放 | 针对设计 | 仓库内独立的 `skill/` 载荷目录 | §13.1 |
| P-24 | trace 顺序未校验，散文与 schema 不一致（C） | 契约有两处定义 | 针对设计 | 校验器检查证据链以 source 开始、以 sink 结束；文档里的枚举表由 schema 生成 | §9.1、§15.3 |
| P-25 | 指令冲突、缺终止条件、模式误触发（C） | 提示词没有显式终态与深度上限；加载即启动全流程 | 针对设计 | guide 与 audit 两种使用方式；每个提示包写明停止条件、深度上限与返回格式 | §4.1、§6.3 |
| P-26 | 执行目标代码的风险（C） | 审计过程会运行不可信代码 | 针对设计 | 默认纯静态只读；动态验证是显式开启的独立阶段，要求操作系统级沙箱 | §8.8、§14 |

26 类问题里，11 类靠取消机制本身即可消除，2 类需要两种处置结合，13 类需要专门的约束或检查。

## 4. 消耗画像

### 4.1 一次大型审计的实测

数据来自 B 的一次真实审计的状态库：目标是一个数千源文件的多语言代码库，划分为 43 个工作单元、11 个批次，首尾事件相隔 6 天。

| 阶段任务 | 任务数 | worker 时长占比 | 模型产出的 JSON |
|---|---:|---:|---:|
| 面发现 | 43 | 4.8% | 1.2 MB |
| 假设生成 | 43 | 5.0% | 1.3 MB |
| 可达性验证 | 374 | 23.1% | 3.2 MB |
| 独立反驳 | 256 | 20.2% | 1.5 MB |
| 反驳裁定 | 117 | 2.7% | 0.8 MB |
| 不可达结论复核 | 47 | 2.0% | 0.2 MB |
| 类别审计 | 319 | 28.7% | 7.7 MB |
| 实验评估 | 374 | 12.5% | 1.7 MB |
| 批次收尾 | 11 | 1.1% | 1.7 MB |
| **合计** | **1,584** | **616 worker 小时** | **19.3 MB** |

从同一份数据还能读出：

- **真正读代码找问题的阶段只占约 10% 的 worker 时长**（面发现加假设生成）。其余 90% 花在对已有假设的验证、反驳、类别复审、实验评估和收尾上。
- **每个假设平均触发约 3.1 个后续任务。** 374 条假设带来 1,168 个验证、反驳、裁定、复核、实验评估任务，每个都在全新上下文里重读同一段代码。
- **反驳阶段很少改变结论。** 256 次反驳里 243 次维持原判，12 次推翻，1 次待复核；这一阶段占 20% 的时长。
- **实验评估阶段几乎没有实验。** 374 个任务一共只登记了 3 个实验；结论分布为不可行 158、保留静态结论 212、待复核 4。
- **类别审计近半数空转。** 319 个任务里 152 个没有任何假设可处理；全部 319 个任务输出里的发现关联字段都是空的。
- **产出质量与投入不成比例。** 374 条假设里 299 条被判“可达”，最终登记 60 条发现，全部是“加固建议、低危、待复核”。
- **最终报告不可读。** Markdown 报告 2.6 MB，发现总览从第 14,715 行开始，之前是逐路径的覆盖与声明表。
- **token 用量完全缺失。** 1,584 个任务都只记录了运行次数和墙钟秒数，没有一个带 token 数。
- **重做成本。** 97 个任务跑了第二次，2 个跑了第三次；另有 87 次租约释放、25 次过期恢复。

### 4.2 多语言试点汇总

B 在 11 个语言槽上各做了一次静态试点，汇总为：2,082 个攻击面 → 763 条假设 → 可达 30.8%、待复核 64.4%、不可达 4.8% → 178 条发现，其中 0 条达到“确认”。试点复盘把主因归结为两点：决定性的一步常在切片之外（外部依赖的行为、宿主配置的默认值）；“待复核”只有自由文本，没有“怎样才能判定”的结构。

### 4.4 宿主固定开销（本机探测）

2026-11 在本机对两种目标 CLI 的无头模式各做了一次最小调用（空任务、要求返回一个两字段的 JSON 对象）：

- 两者都能在进程输出里给出 token 用量，其中一种还给出费用、模型上下文窗口和子 agent 统计。用量可以由程序读取，不需要 worker 自报。
- 单次调用有固定的输入开销。在同一种 CLI 上，默认工具集时约 11.7k token，把工具集限制为三个只读工具后约 3.2k；另一种 CLI 在默认配置下约 6.5k。任务切得太碎，固定开销占比就会很高；限制工具集同时降低开销和风险。
- 结构化输出不一定被强制：一种 CLI 严格按 schema 返回，另一种在当时的后端上返回了代码围栏包裹的 JSON。CLI 背后可能是任意供应商甚至本地模型，不能假设宿主会保证格式。
- 认证信息可能放在用户级配置里。忽略用户配置的“最严隔离”开关会直接导致未登录；用户级的默认权限模式也可能在无头或高权限环境下被拒绝，需要显式指定。

### 4.5 消耗根因与对策

| 编号 | 根因 | 实测证据 | 对策 | 目标值 |
|---|---|---|---|---|
| C-01 | 每个假设在多个全新上下文里被反复重读 | 3.1 个后续任务/假设 | 验证与证伪合并为一次，按代码位置成簇；只有高危结论做第二意见 | 每个候选平均不超过 1.3 个验证任务 |
| C-02 | 假设没有准入门槛，便宜地产生、昂贵地处理 | 374 条假设 → 60 条低价值发现 | 候选必须给出 source、sink、缺失的守卫和安全后果，否则只记一行加固备注 | 候选确认率作为自审指标持续跟踪 |
| C-03 | 强制阴性表态与全量枚举 | 19.3 MB 输出，类别审计占 40% | 稀疏输出：只写阳性与例外 | “无发现”单元的输出不超过 1 KB |
| C-04 | 同一范围被多个阶段各读一遍 | 面发现、假设生成、类别审计 | 一个 hunt 任务读一次，直接产出候选 | 发现阶段占 worker 投入不低于 60% |
| C-05 | 无效任务 | 实验评估 99% 无实验；类别审计 48% 无假设 | 任务只在有输入时创建 | 无效任务不超过 5% |
| C-06 | 模型充当协调者 | 91 KB 文档、80 个命令、每任务至少两次命令往返 | 调度循环交给程序；入口文档不超过 12 KB | 协调上下文不随任务数增长 |
| C-07 | 校验失败只能整份重做 | 99 次重复尝试 | 提交时校验，结构错误在原会话修复 | 整份重做不超过 3% |
| C-08 | 批次收尾材料由模型撰写 | 每批收尾输出中位数 163 KB | 汇总、对账、报告全部由程序派生 | 模型撰写的收尾为 0 |
| C-09 | 深度不分级 | 43 个单元全部走完所有阶段 | 风险分层，预算按层分配，缺口显式报告 | 见[系统设计 §5.5](./SYSTEM_DESIGN.md) |

## 5. 继承与舍弃

**继承的做法**

- 来自 A：模型是主分析引擎，规则只做提示；从输入面出发而不是全库规则扫描；按目标形态（应用、库、混合）确定可达性规则；独立视角的证伪；同类变体搜索；报告从单一事实源机械渲染；“过设计、设计偏见、死代码、盲目带入”四项评估和新增义务的准入提问。
- 来自 B：状态放在目标仓库之外；默认全新审计，后续审计必须显式声明历史来源；未知与不支持显式化；证据锚点对冻结快照做存在性校验；skill 问题与漏洞假设分开记录；发现分为安全漏洞、普通缺陷、加固三类；测试路径是否纳入范围由操作者决定；评测答案与运行时知识隔离。
- 来自 C：guidance 与 full audit 两种模式；确认、待验证、驳回三分支裁决；待验证必须写明确切的阻断事实与验证计划；严重度不超过已证明的影响；证据链顺序校验；零依赖校验器；带预留的预算；显式的未完成状态；提示词里的终止条件、深度上限与字面返回格式；指纹不含行号。

**舍弃的做法**

- 独立的类别复审阶段、逐假设的实验评估阶段、默认的多上下文反驳加裁定。
- 任务租约、宿主认证、签名观察、追加式修订与阶段修订、交接对象协议。
- review altitude、路径风险分层这类只能校验形状的自我声明。
- 审计教训与覆盖账本写回 skill 资产；仓库内保存被审项目名的黑名单。
- 每版一套设计件、版本守卫测试、资产计数断言。
- worker 输出的容错归一器。
- 由模型执行的协调手册；把大段正文原样拷入每个提示词；由父 agent 手写 JSON 账本。

## 6. 对新设计的约束

1. 长循环不进模型上下文：调度、对账、渲染由程序完成。
2. 模型输出与发现数量成正比，不与清点规模成正比。
3. 任务只在有输入时创建；每个候选的验证次数有上限。
4. 用量由程序采集，预算是运行的必填输入，超限即停并照常出报告。
5. skill 载荷运行期只读，不存在任何写回通道。
6. 知识条目正向准入，仓库内不出现真实项目名单。
7. 每类记录只有一份契约，校验严格，错误就地修复，不做容错归一。
8. 状态模型保持最小，受影响部分重算而不是修订。
9. 门禁全部机械化，并且每个都有必须失败的反例。
10. 文本、命令、字段、阶段都有预算，增长需要显式决策。
