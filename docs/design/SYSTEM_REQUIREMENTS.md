# 系统需求规格

> 状态：评审草案，不代表实现或验收通过。本文中的 SR-001～SR-030 是本项目的系统需求基线；原 [系统设计 §1.2](./SYSTEM_DESIGN.md) 的 SR-01～SR-10 为概括性历史编号，不再作为逐项验收编号。需求优先级均为首版必需，另有明确说明者除外。
>
> 来源：用户目标及后续评审、[系统设计](./SYSTEM_DESIGN.md)、[决策记录](./DECISIONS.md)、[前代复盘](./PREDECESSOR_RETROSPECTIVE.md)。实现方案与追踪关系见[软件设计](./SOFTWARE_DESIGN.md)；设计检查见[设计审查](./SOFTWARE_DESIGN_REVIEW.md)；开发拆解见[软件开发需求](./SOFTWARE_DEVELOPMENT_REQUIREMENTS.md)。

## 1. 范围与约定

系统是安装在 Claude Code CLI 或 Codex CLI 环境中的通用源码安全审计 Skill，由静态审计工作流、可移植知识、确定性工具包和宿主适配组成。面向单语言和混合语言的中小型至超大型仓库；规模扩大时允许预算限制下的部分审计，但必须如实展示缺口。guide 是轻量问答，audit 才产生正式卷宗。首版不实现动态运行目标代码、在线探测、历史状态增量复审或第三方框架专属知识包。

“必须”是可检验约束；“目标”是待评测假设，不是现有能力或质量承诺。语言 Top10 表示初版十个有公开依据、经评审的优先关注类，并非已证明的客观排名；审计不因缺乏卡片而排斥其他问题。

## 2. 功能与交付

| 编号 | 需求及验收准则 |
|---|---|
| SR-001 | 明确区分 guide 与 audit：前者不创建正式运行卷宗，后者需显式范围和预算；模糊请求由宿主确认。验收：两种输入分别触发相应行为，模糊输入不静默启动完整审计。 |
| SR-002 | 首版提供现有名册 15 种语言、每种 10 个经评审的语言相关问题类；记录公开依据、适用条件、误报条件和合成正反例。验收：150 个唯一编号的条目齐全并通过逐语言人工评审与质量检查；称为草案直至通过。 |
| SR-003 | 审计可处理多语言边界及目录外风险；TypeScript 应同时考虑 JavaScript 运行时风险，其他基座关系仅在适用平台生效。验收：混合语言与目录外合成漏洞能进入同一候选和验证流程，语言映射不把所有 Kotlin/Scala 目标误判为 JVM。 |
| SR-004 | 清点范围、排除项和原因，识别语言、组件及扫描信号，按可解释风险和预算计划审读。验收：清点总数、纳入和排除按相同快照对账；无信号不等于安全；未知语言单列且可采用通用方法。 |
| SR-005 | 支持大文件分块、较大仓库的分批处理及跨语言、跨单元追踪。验收：分块覆盖所有纳入行范围并记录重叠；构造的跨单元 source→sink 和混合语言夹具可产生可追踪的待验证连接，未连接或超额条目有明确状态。 |
| SR-006 | Recon 从本次目标提取攻击者模型、入口、环境守卫及其范围、例外和证据；它们不构成自动豁免。验收：有锚点的已启用守卫、适用例外、未知状态均能保留；未经路径适用性核验不得据此驳回。 |
| SR-007 | Hunt 支持正向候选、强信号反向悬空 sink 和边界 frontier；信号和连接均只是线索。验收：缺 source 的半链不被伪装成完整发现；数量限制、截断或预算导致的遗漏可追踪，不静默丢弃。 |
| SR-008 | 验证由独立于发现任务的新上下文进行证伪和证据推理，区分 confirmed、needs_validation、rejected 及未验证。验收：每种裁决满足其条件，未解决的可达性或防御条件不得标为 confirmed；锚点存在本身不构成证明。 |
| SR-009 | 支持经独立静态验证的 E2 确认，不要求首版动态复现；证据等级与裁决分开。验收：E2 记录攻击者、逐跳数据与控制流、适用守卫及前提，无法支撑的论断转为待验证；首版不得宣称 E3。 |
| SR-010 | 对确认发现报告 source、sink、跨文件/语言有序证据、守卫、攻击前提、影响、修复建议和回归建议，分别呈现严重度及修复紧迫度。验收：逐字段追溯至记录与证据；密钥值不得出现在报告。 |
| SR-011 | 严重度与紧迫度基于明确因子和规则，允许受约束的人工调整并保留规则值、调整值及理由；待验证项仅给验证优先级。验收：计算可复现、调整有审计记录，缺失因子或理由拒绝定级。 |
| SR-012 | 生成面向用户语言的主报告、机器可读结果、未决事项、覆盖、轨迹、成本和 Skill 自审；在受控中断、预算耗尽或任务失败时输出不完整报告。验收：报告与持久状态对账，说明终态和缺口；存储损坏或不可写时显式报错而非伪称已生成。 |
| SR-013 | 保留审计卷宗及结论到任务、提示、结果、源快照和锚点的追溯关系。验收：任一发现可追至快照文件摘要、候选及独立验证；驳回理由、失败与未决记录可查询。 |
| SR-014 | 每次可结束的运行都生成 Skill 自审，至少覆盖成本、流程、质量、覆盖缺口和适配能力，数据不可得时标明原因。验收：正常及不完整运行均能生成；故障导致无法生成时显示故障及恢复路径。 |

## 3. 质量、安全与运行约束

| 编号 | 需求及验收准则 |
|---|---|
| SR-015 | 载荷、源码、运行目录分离；正常审计不向载荷和目标写入、不执行目标代码、不默认在线探测；目标文本视为不可信数据。验收：路径别名/符号链接攻击与目标内指令注入反例无法通过受支持隔离配置修改目标或载荷；无法强制的权限在启动前披露并需用户明确接受。 |
| SR-016 | 新运行不读取旧运行，Skill、测试和设计资产不引入历史审计目标的信息；运行卷宗只在用户控制的位置保留。验收：无自动回写通道；导出只允许有限的无自由文本字段，经审核后才可用于升级；检查不得宣称自动证明零泄漏。 |
| SR-017 | 开始前固定可校验的源码视图，恢复时保证输入与证据指向同一视图。验收：dirty Git、非 Git、同大小且相同时间戳的修改和中途变更均被快照内容摘要检出或不影响已冻结内容；不能确保一致时拒绝继续。 |
| SR-018 | 在中断、重复提交、并发领取、延迟提交、驱动切换及进程崩溃后保持状态一致，不重复接受同一任务的有效结果。验收：故障注入和并发测试证明原子状态变迁、过期尝试被拒绝、恢复后可审计对账。 |
| SR-019 | 预算须可在派发前预留，并对不可度量或不可强制的预算维度诚实降级。验收：多并发及重试下可强制预算不超上限；无可靠用量/限额时不能称 token 或费用为硬上限，需阻止该模式或经同意切换到可执行的任务/时间限额。 |
| SR-020 | 低自耗：减少模型承担的调度和清点、稀疏输出、限制任务扇出，并记录可得的输入、输出、缓存、重试和费用。验收：指标注明分子、分母、数据来源和缺失率；未知值不写成零，目标是否达成由独立评测判断。 |
| SR-021 | 覆盖按快照、范围、组件、语言和实际证据定义，区分清点、扫描、已提供上下文、可观测读取和模型审读声明；报告未知或未完成。验收：仅文件打开不推断整文件审读；排除、失败、分块重叠和日志缺失不会虚增覆盖。 |
| SR-022 | driver 与 in-session 为同等支持的工作方式，共用审计语义和持久记录，运行前探测宿主能力。验收：同一合成案例分别完成相同状态与报告契约；宿主不支持委派或隔离时显式说明降级，不能把设想当作已验证。 |
| SR-023 | 适配 Claude Code CLI 和 Codex CLI 的已验收版本，明确能力矩阵、认证、结构化输出及不加载目标指令的条件。验收：真实 CLI 集成测试和不可信目标指令反例通过，不能做到的能力标为不支持；不得自动降低隔离级别。 |
| SR-024 | 标准库实现核心工具包，离线可使用；与两种宿主对接不要求安装第三方 Python 包。验收：在明确支持的 Python 版本和干净环境运行确定性测试；版本下限经兼容测试后公布。 |
| SR-025 | 结构化输入严格验证类型、限制、条件字段、语义和跨记录关系；无效输入可定位、不可静默修复成有效结论。验收：缺字段、越界、错误锚点、失效 attempt、错误定级等反例均被拒绝并记录原因。 |
| SR-026 | 门禁检查记录完整性而不是证明安全；部分运行允许生成如实标注的报告。验收：每个门禁有通过/反例、可定位失败和明确完整/不完整结果，不以门禁通过宣称零漏洞。 |
| SR-027 | 状态、卷宗与知识资产有版本和兼容策略，升级不隐式迁移未完成审计或篡改历史记录。验收：受支持旧格式的读取/重渲染有测试，不支持的版本显式拒绝，升级需用户确认。 |
| SR-028 | Skill 升级只接受项目无关的问题抽象和合成回归例；同类问题来自至少两次独立运行或属于阻断性缺陷，例外须记录。验收：准入记录、独立性证据及回归结果可审查；不因单次结果加入目标专属条款。 |
| SR-029 | 在合成正反例、留出语料、大规模目录和双宿主上评测功能、恢复、安全与成本；留出集与调参隔离。验收：发布报告给出各语言及跨单元的分母、检出、误报、未决、成本和环境；无可靠数据不得宣称召回率或通过目标。 |
| SR-030 | 规模和成本阈值须有明确测试条件、基线、统计口径与未达标处理。验收：十万文件只作为确定性规模测试场景，不等于超大仓库审计能力保证；拟定的 15%、60%、1.3 等数字在评测确认前均为假设。 |

## 4. 需求边界和验收状态

用户要求保留历史项目信息之外的可追溯运行证据；因此本地 run 可以包含目标材料，通用 Skill 资产不能包含。所有需求当前均为**未实现、未验收**。文件系统隔离、模型推理准确率、CLI 实际能力、用量强制和极大规模性能均需按设计审查中门禁验证；不能由文档本身保证。
