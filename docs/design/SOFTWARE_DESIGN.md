### 1.1 数据流

`配置 → 能力检查 → 冻结快照/清点 → Recon → Hunt → 合并/连接 → 独立 Verify → 报告/自审`。状态与预算在每个边界上原子检查；driver 和会话内引擎复用同一调度器及验证器。流程可暂停或预算终止；停止后在可写的持久状态上尽力生成不完整报告。快照或存储不可用时返回可诊断错误，不虚构产物。

## 2. SD-01、SD-02：入口、知识与适用性

配置至少包含目标路径、纳入/排除规则、语言或区域偏好、报告语言、运行目录、模式、预算及宿主能力选择。路径规范化后检查目标、载荷、运行目录互不重叠，也检查解析后的路径和已存在父目录；创建和访问时仍需防止符号链接替换。预算与安全降级不使用静默默认值；用户不接受降级则停止。具体版本或 CLI 参数须通过实测矩阵确认，不能以当前草案中的示例参数为兼容性证明。

目录采用 15 × 10 的稳定条目 ID；卡片含来源、适用范围、漏洞和安全合成例、边界及误报条件。程序检查完整性、引用与基本格式，语言专业评审负责判断实际特异性、准确性与优先级；“三种接口”“相似度阈值”不能单独证明质量。TypeScript 加载 JavaScript 索引；Kotlin/Scala 的 Java 索引仅对 JVM 目标适用，C++ 的 C 接口风险仅在使用相应接口时适用。平台未知则说明不确定，而不是断言继承。平台判定以冻结快照内的构建标识为证据（pom.xml、Gradle 构建/设置脚本、`*.sbt`、`.mvn/` 族）：有 JVM 构建标识判为 JVM，无证据判为未知并按不确定处理——不展开 Java 基座索引并在 packet 行披露 platform unknown，检测依据与结果进入计划记录 **[DA-03]**（落实本节“平台未知则说明不确定”）。通用业务逻辑和授权问题可不经目录进入候选。

## 3. SD-03：不可变视图、计划与覆盖分母

1. 在运行目录建立私有只读快照：逐个复制常规文件并计算内容摘要，记录规范相对路径、文件类型、大小、摘要、排除与读取错误。Git 提交及 dirty 状态仅作附加元数据，不能代替内容；不依赖 mtime/大小证明一致。遇到符号链接默认记录并不跟随；是否提供受约束跟随选项须另经安全设计。快照只给 worker 读，来源目录和其他本机文件不因提示而授权。
2. 源目录构建期间可能变化：先列清单并采集，再复查清单与摘要；发现变化、不可读文件、特殊文件或不能保证一致时记录并中止准备，用户重试或调整范围。即使复查也不是原子文件系统快照；一致性依赖输入在采集期间稳定或底层原子快照能力，前提及未覆盖范围须明确。冻结后只引用复制品。采用流式处理、临时文件与原子发布；存储不足须失败，不能退回弱快照。
3. 清点分母为快照清单中**明确纳入**的常规源码文件及其行区间；排除、无法纳入及未知语言单列，不能悄悄并入已审读分母。分块以启发式符号识别或固定窗口为候选切点，使用区间并集证明无漏行；重叠只算一次。正则不提供解析正确性保证。
4. 风险信号仅排序，按组件、语言及边界生成确定性单元。计划及所有被限额延后任务保留原因。十万文件性能以给定硬件、文件大小分布、计时和峰值内存实测；阈值和目标机器须在评测方案确定，不能从数量推断 LLM 全量覆盖。

## 4. SD-04、SD-05：分析、证据、裁决

Recon 记录 `guard_id, anchor, mechanism, applicability, exceptions, status`，状态区分观察到、未发现和未知；锚点可校验存在但不能证明守卫被启用。提示包可压缩守卫摘要，溢出时记录遗漏并通过引用按需读取，不可省掉影响安全判断的事实。

Hunt 输出三类不同记录：完整候选（source、sink、局部链、潜在影响和待证条件）、悬空 sink（局部敏感操作及反向边界，不假装有 source）、frontier（source 到边界的局部证据）。机械连接使用具名符号、参数、边界元数据生成**假设边**，歧义、多对多和跨语言转换须交 verifier 求证；无匹配、上下文不足、上限溢出及未安排验证保持可追踪的待办/覆盖缺口。数组上限是单次传输限制：由分页或拆分任务处理；不能分页时记录具体溢出区域和数量下界，进入 incomplete，而不是丢弃。半链即使无法证明局部无守卫也可保留并标未知，不被降成普通加固备注。

候选机械预检检查模式、范围及锚点是否指向冻结快照；不满足时给诊断、允许修复或进入未验证，不将其视为已证伪。指纹只生成去重建议，保留原始记录和 source 区别；合并须保留来源，无法确定不合并。

Verifier 与 hunter 使用独立调用及上下文，独立不意味着不同模型或绝对无偏。它逐跳说明调用与数据传递、攻击者控制、路径条件、守卫实际适用、后果及前提，并主动寻找反证。机械规则仅检查引用和结构，不证明语义可达或守卫缺失。静态证据足够且所有决定性前提明确可满足时可 `confirmed/E2`；必要事实缺失、依赖行为或配置不确定、路径/防御无法判断时 `needs_validation/E1` 并列阻断与计划；有可核验反证才 `rejected`；未执行验证保留 `unverified`。不强制声称不存在任何守卫，而是对所研究的路径和可见范围作证据支持的判断。

分级记录 `impact, exploitability, factor_reasons, calculated_severity, calculated_urgency, adjustment?, final_severity, final_urgency`。使用[原系统设计 §9.2](./SYSTEM_DESIGN.md) 的矩阵作为待评审规则；调整最多一档、记录操作者及理由，并明确只调整最终严重度，最终紧迫度由最终严重度和可利用性重新计算。条件字段按裁决分别校验：未决项不具修复紧迫度，驳回项需反证，确认项需修复和证据。规则与调整字段均保留，不将最终值误校验成规则值。

## 5. SD-06、SD-07：持久性、领取与预算

### 5.1 实体和事务

实体包括 run、snapshot、unit、task、attempt、candidate、finding、usage、artifact；事件只追加，状态视图可重建。所有状态变迁和预算记账在 SQLite 事务中提交，外部文件先写临时文件、fsync 后原子重命名，再用事务引用内容摘要；孤儿文件可回收但事件不得引用未发布文件。数据库与文件不是同一原子事务，恢复必须检查引用和摘要，缺失时显式损坏并停止相关工作。WAL 和 busy timeout 是可用的争用配置，不是单独的并发正确性保证；不支持的文件系统须探测或拒绝。

任务生命周期 `queued → claimed → running → done | failed | quarantined | cancelled`；中断后可重排但保留每次 attempt。claim 在事务中验证状态并生成随机 claim token、单调递增 generation、有效期限及预算预留；提交携带 run/task/attempt/generation/token 和结果摘要。事务内核对当前 attempt 与期限；重复相同提交返回原回执，不同内容冲突，过期或已被替换的提交拒绝并记录。期限到后可原子撤销并重新领取，迟到 worker 不能覆盖新结果。可选续期需同样校验 generation；时钟异常或协调者不可信时保守暂停，不能只依赖墙钟证明安全。密钥不写普通报告。driver 单写队列减少竞争，但两个 driver 或会话内多进程仍由同一数据库 claim 事务约束。

运行终态为 `complete` 或 `incomplete(reason[])`；前者只表示计划范围的处理与门禁完整，不表示安全。运行可暂停、中止和恢复；恢复重建状态并校验快照、契约与已发布产物。快照不可变，同一次运行不接受漂移替换；变化需要新 run，原 run 仍可用其冻结快照恢复。新版本只在明确支持的 schema 范围内读取或重渲染，未完成任务不自动跨版本迁移。

终态判定前置两条计划覆盖不变量 **[DA-01]**：其一，`finalize` 的 `complete` 要求计划范围处理完成——plan_units 与 done 任务对账，从未派发或未达 done 的单元（verify 亦接受显式 quarantine）一律进入 `incomplete(unprocessed_units)`，不因零派发下 lost=0、任务数对账相等而判 complete；其二，有效租约内存在 claimed/running 在途 attempt 时 `finalize` 直接以 `INVALID_STATE` 拒绝（先 pause 或等租约过期后 reclaim），在途任务不得被当作已收敛。

### 5.2 可执行的预算语义

每维区分 `enforced`、`observed`、`unavailable`；每项记录上限、来源、单位、已结算、未结算和保留。仅当宿主提供可验证的单次调用硬限额、可靠计量和可控子调用且总限额能由调度器约束时，才提供 token/费用硬预算。一次 claim 必须事务性预留该 attempt **最坏可强制上限**；`已结算 + 未结算保留 + 新预留 ≤ 总限额`，验证预留单独保护，重试再次预留。完成以可信宿主数据结算；用量丢失、超额、子调用不可控或进程失联时保留最坏额并暂停该维度，不能假设为零或重新派发导致超支。若上游硬限额本身不可靠，只能标为软预算。

若无法满足硬 token/费用模式，启动前拒绝，或经用户明确选择任务数与墙钟限制的降级模式；墙钟停止派发并请求取消，实际退出时间取决于宿主，非严格成本上限。成本报告分别标记确值、估计和不可得；协议开销仅在来源能区分时计算。确认预算先于优化指标，预算不足保留未验证候选，输出 incomplete。

## 6. SD-08：覆盖、卷宗和报告

每个区间分别记录 `inventoried`、`signal_scanned`、`context_supplied`、`observed_read` 和 `review_claimed`，注明来源、行区间、任务 attempt 和可信度。工具日志只能证明读取动作或其可见范围，无法证明模型理解；无可用日志为 unknown，不能用自述替代观测。范围并集计算去重后的文件/行分母，部分文件不算整文件覆盖。优先报告高风险未处理单元、排除、失败、分页溢出及半链。

报告由记录派生并逐项对账；主报告、JSON、覆盖、未决、轨迹、成本和本地 Skill 自审各带快照/运行 ID、时间、状态与限制。结论来源包括原任务、提示包、原结果、证据快照摘要与独立验证。卷宗可能含敏感代码：默认只在用户指定的目标外私有目录写入，访问权限及保留期由部署环境和用户控制，报告不复制凭据值。存储出错时返回非成功状态并保留可恢复诊断，不承诺一定能写完所有报告。

## 7. SD-09：双宿主、工具与信任边界

driver 运行独立 CLI worker；in-session 经 `next → execute → submit` 调度。两者使用相同快照、claim 协议和状态；可暂停后切换，但不同时接管活跃 claim。若宿主不支持委派，可由主会话有限顺序执行，标记此能力及成本差异，不称作具有子 agent 的等价实现。CLI 参数、日志、配置加载和认证仅以被测版本的能力矩阵为准。

可选 MCP 是传输适配，不是安全沙箱：只暴露绑定当前 run 的领取、提交、状态、受限读取接口，规范化路径、限制请求大小和任务所有权；不提供任意文件/命令接口。线协议采用标准 MCP：`initialize` → `tools/list` → `tools/call`，通知帧零回包，旧式直连方法保留兼容 **[DA-02]**。访问控制依赖可信宿主、操作系统权限和部署方式；本地 stdio 本身不证明调用者身份或限制其他工具。提示中的“只读”不能阻止恶意代码指令、命令工具或网络；默认禁止执行目标代码，但对实际执行、文件写和网络的强制保证必须由已验证的宿主权限或 OS 沙箱提供。doctor 报告 `enforced / not_enforced / unknown`、网络/写入/执行各自状态；未知不得冒充受控。隔离不足时暂停并征得用户选择，禁止静默降级；MCP 的实现和平台兼容性是发布前验收项，不是预先保证。

## 8. SD-10、SD-11：契约、门禁、自审与升级

唯一版本化 JSON Schema 是交换契约。标准库校验器须支持**契约实际使用的完整子集**，包括嵌套对象/数组、必需/额外属性、类型、枚举、界限和条件字段；不支持的关键字在加载时失败。可采用受限子集和语义校验器，不声称完整 JSON Schema 兼容；用官方适用子集测试和本项目反例交叉验证。结构化输出由适配层严格提取，超限、截断或语义失败有诊断与有界重试，不自动修成成功结果。

G0 快照及清点、G1 任务/覆盖、G2 验证与证据结构、G3 报告对账、G4 自审与导出边界。门禁只检测可程序化的不变量；未计划或预算耗尽项可以标为已记录的 incomplete，而非强行视为 complete。失败可出不完整报告；无法安全渲染时返回错误。每一门禁有正常和必须失败的测试。

自审本地部分可含卷宗引用；默认不自动导出自由文本。可移植导出只含固定枚举、经约束的整数/统计及版本化字段，不含路径、名称、标识符、源码、引文、自由文本或原始提示；禁止稀有高基数数据、细粒度唯一计数等未经隐私评估的字段。允许列表和去标识化只是防护，不可证明匿名：默认仅本地，跨运行或仓库导入须用户/维护者审核，无法判定安全则不导出。合成回归由维护者独立编写，禁止复制目标内容；两次独立运行或经记录的阻断性例外才准入，仍需通用性评审。

## 9. 评测及可追踪关系

验证层次：确定性单元/属性与故障注入；多进程领取和提交；快照漂移与路径逃逸；覆盖及黄金报告；语言合成正反例；未参与调参的外部留出集；真实 Claude/Codex 各自 driver 和可用的 in-session 组合。只测试已实际支持的组合，不把未提供的宿主能力填成通过。评测定义样本、运行版本、硬件、预算、可用度量、分母和置信限制；成本指标目标未定前为实验假设，严禁为达指标压缩证据或静默漏报。

系统需求到设计的完整关系为上表 SD-01～SD-11；每个 SR 的逐条开发、验收及依赖见[软件开发需求追踪矩阵](./SOFTWARE_DEVELOPMENT_REQUIREMENTS.md)。未决发布风险和审查结论见[设计审查](./SOFTWARE_DESIGN_REVIEW.md)。
